Every programmer makes mistakes all day; the skill is reading the message and fixing them quickly. MiniLang checks your program in stages, and every message names its stage and its line. Most stages also keep going after the first problem, so you see every mistake at once.

StageWhenTypical cause
Lexerbefore runninga character MiniLang doesn't use, such as & or "
Parsebefore runningthe grammar is wrong: a missing ;, brace or bracket
Semanticbefore runninga name that is never defined, or a call with the wrong number of values
Typebefore runninga list used where a number is needed, or the other way round
Runtimewhile runningdividing by zero, an index out of range, running out of input

Errors found before running

The first four stages read the program without running it. If they find anything, nothing runs. They often suggest a fix:

{% call g.example(expect="lex") %} x = 4; if x > 1 && x < 9 { print x; } {% endcall %} {% call g.example(expect="parse") %} whiel x < 3 { x = x + 1 } {% endcall %}

Two mistakes, two messages: a misspelled keyword and a missing ;. Fix the first message first, because a later one is sometimes just a knock-on effect of it.

{% call g.example(expect="semantic") %} total = 0; func average(a, b) { return (a + b) / 2; } print avrage(4, 8); print average(4); {% endcall %}

Errors while running

A runtime error stops the program at that line. Everything printed before it stays, which helps you work out how far it got. In the playground, the step-through shows exactly what the program was doing just before.

{% call g.example(expect="runtime") %} xs = [5, 10, 15]; for i = 0; i <= len(xs); i += 1 { print xs[i]; } {% endcall %}

The loop runs one time too many: <= should be <.

Warnings

A warning doesn't stop the program, but it points at something that is probably a mistake: a variable that is never used, code that can never run, or a value that is overwritten before anyone reads it.

{% call g.example() %} result = 0; result = 6 * 7; spare = 5; print result; {% endcall %} {% call g.remember() %}
  • Every message gives a stage and a line number: start there.
  • Fix the first error first; later ones may disappear with it.
  • Runtime errors keep the output printed before them; step through to see why.
  • Warnings don't stop the program, but are usually worth fixing.
