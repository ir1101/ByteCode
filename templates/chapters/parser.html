The lexer produced a flat list of tokens. But programs aren't flat: a loop contains statements, an expression contains smaller expressions. The parser checks that the tokens are in an order the language allows, and builds a syntax tree that shows how they nest. MiniLang uses a hand-written recursive descent parser: no parser generator, just one Python method per grammar rule.

{{ g.h2("Grammars") }}

A grammar describes every valid program with a handful of rules. Each rule says what one construct is made of. Here is MiniLang's, exactly as it appears at the top of parser.py:

{{ g.source("parser.py", start="program := ", end="call := ") }}

How to read it: := means "is made of", | separates alternatives, ( … )* means "repeated zero or more times", ? means "optional", and words in quotes are tokens. So while := "while" expr block says: a while statement is the keyword while, then an expression, then a block.

The trick of recursive descent is that every rule becomes a method that reads exactly what the rule describes. Compare the while rule with its method:

{{ g.source("parser.py", "Parser.while_stmt") }}

expect consumes a token that must be there, or reports an error. self.expr() and self.block() call the methods for those rules, and those call others in turn. The "recursion" in the name is that a block contains statements, which can contain blocks again, so the methods call each other as deep as the program nests.

Which rule applies is decided by looking at the current token. A statement starting with while must be a while statement; one starting with a name followed by ( must be a call. One token of lookahead (two, for a call) is always enough, which is why there's never any guessing or backtracking:

{{ g.source("parser.py", "Parser.statement") }} {{ g.h2("Precedence by layering") }}

1 + 2 * 3 must mean 1 + (2 * 3). The grammar builds this in by splitting expressions into layers, from loosest to tightest: or, and, not, comparisons, + -, * / %, unary minus, indexing, and finally single values. Each layer's method parses its operands by calling the next, tighter layer:

{{ g.source("parser.py", "Parser.additive") }} {{ g.source("parser.py", "Parser.term") }}

When additive asks term for an operand, term swallows the whole 2 * 3 before returning. So by the time additive sees the +, the multiplication is already a finished subtree:

{% call g.stage("ast") %} print 1 + 2 * 3; {% endcall %}

The while loop in each layer also fixes associativity: each new operator takes everything parsed so far as its left side. So 10 - 4 - 3 becomes (10 - 4) - 3, which is 3, and not 10 - (4 - 3), which would be 9:

{% call g.stage("ast") %} print 10 - 4 - 3; {% endcall %}

Brackets need no special rule: primary sees a ( and simply calls expr() again from the loosest layer.

{{ g.h2("Building the tree") }}

Each method returns a node, and nodes hold the nodes of their parts, so the tree builds itself as the methods return. The node classes live in ast_nodes.py. Each one lists its fields, and every node remembers its line:

{{ g.source("ast_nodes.py", "Node") }} {{ g.source("ast_nodes.py", start="class If(Node):", end="fields = (\"condition\", \"body\")") }}

The tree keeps only what matters. Brackets, semicolons and braces have done their job of showing the structure, so they aren't in the tree at all:

{% call g.stage("ast") %} if x > 0 { print x; } else { print -x; } {% endcall %}

Again, x doesn't need to exist yet: the parser checks shape, not meaning. This tree is what the next four stages work on.

{{ g.h2("Syntactic sugar") }}

Some syntax is only a shorter way to write something the language can already say. x += 1 means exactly x = x + 1, so the parser builds the tree for the longer form, and no later stage ever needs to know += exists. This is called desugaring:

{{ g.source("parser.py", "Parser.assignment", start="if op.value in COMPOUND_OPS:", end="value = BinOp(") }} {% call g.stage("ast") %} x = 5; x += 2; {% endcall %}

The second statement's tree is an ordinary assignment of x + 2. The else if chain is handled the same way: an else whose body is another if.

{{ g.h2("Error recovery") }}

When the tokens don't fit the grammar, the simplest parser would stop at the first problem. MiniLang's keeps going, so you see every syntax error in one run. It uses two classic strategies.

Phrase-level recovery. A ; missing at the end of a line is by far the most common slip. When expect wanted a ; and the next token is on a later line, it records the error and carries on as if the ; had been there:

{{ g.source("parser.py", "Parser.expect", start='if value == ";" and', end="return None") }}

Panic mode. For any other error, the statement is abandoned and the parser skips tokens until a new statement could start: just after a ;, or at a brace or a statement keyword. Then it continues as normal. Only the first error on each line is kept, because the rest are usually knock-on effects:

{{ g.source("parser.py", "Parser.synchronize") }} {% call g.stage("ast", expect="parse") %} x = 1 y = 2 +; whiel y > 0 { y -= 1; } {% endcall %}

Three errors, each on its own line: a missing ; (repaired), a broken expression (skipped to the ;), and a misspelled keyword that gets a "did you mean" hint from difflib.

  • A grammar's rules describe every valid program; recursive descent turns each rule into a method.
  • The current token decides which rule applies, so there's no backtracking.
  • Precedence comes from layering: each layer calls the tighter one for its operands.
  • The tree keeps structure, not punctuation, and every node keeps its line.
  • Errors are repaired (a missing ;) or skipped past (panic mode), so all of them are reported.
