The code generator (next chapter) translates the program faithfully, one construct at a time. That's correct, but often wasteful: it computes 2 * 3 every time the line runs, stores values nobody reads, and jumps to jumps. The optimizer makes the program smaller and faster, under one strict rule: it must never change what the program prints, or which error it raises.

Its passes run in this order, each feeding the next:

{{ g.source("optimizer.py", "optimize") }}

The first line compiles the original tree once just for its checks, so that optimizing can never hide an error. Then come constant propagation (chapter 5), constant folding, dead-store elimination, code generation, and finally a peephole pass over the bytecode. Each "Try it" below shows the bytecode the optimizer produces, with the size before optimizing in the first line.

{{ g.h2("Constant folding") }}

Constant folding does arithmetic at compile time. If both operands of an operator are literal numbers, the folder computes the answer once and puts a single number in the tree. It uses the VM's own apply_binary, so -7 / 2 folds to exactly what the VM would compute.

{{ g.source("optimizer.py", "Folder.binop") }}

Notice the guard: x / 0 is never folded. Folding it would either crash the compiler or silently remove the error, and the rule says the program must fail exactly as before, at runtime, with its line number. Folding combines with constant propagation, which turns provably constant variables into literals first:

{% call g.stage("optimized") %} width = 6; height = 7; print width * height + 2 * 3; {% endcall %}

Everything collapses into PUSH 48. Even the stores of width and height are gone, which is the next pass.

{{ g.h2("Dead-store elimination") }}

Once propagation has replaced every read of width with 6, nothing reads width any more, so storing it is wasted work. Liveness analysis (chapter 5) finds such dead stores, and this pass deletes them. It repeats, because deleting y = x can make the earlier x = … dead too:

{{ g.source("optimizer.py", "remove_dead_stores") }}

But a store may only be deleted if computing its value is harmless: it can't fail and has no side effects. x = a / b might divide by zero, x = xs[i] might be out of range, and x = f() might print. Deleting any of those could hide an error or lose output, so only these are allowed:

{{ g.source("ir.py", "harmless") }} {% call g.stage("optimized") %} spare = [1, 2, 3]; d = 0; unused = 10 / d; result = 0; result = 6 * 7; print result; {% endcall %}

spare and the first result are gone, but unused = 10 / d stays even though nothing reads it: running it must still raise "division by zero" on line 3.

{{ g.h2("Peephole optimization") }}

The last pass looks at the finished bytecode through a small "peephole", a few instructions at a time, and rewrites wasteful patterns. It repeats until nothing changes:

  • Constant branches: a constant pushed straight into JUMP_IF_FALSE decides the jump now. This removes if 0, while 0, and the test inside while 1.
  • Jump threading: a jump to a JUMP goes straight to that jump's target.
  • Jumps to the next instruction do nothing, so they're removed.
  • Unreachable code: anything no path can reach is deleted, including code after a return and functions that are never called.
{{ g.source("optimizer.py", "_thread_jumps") }} {{ g.source("optimizer.py", "_remove_unreachable") }}

Deleting instructions shifts every address after them, so every jump and call target has to be renumbered. _compact does that, sending a jump aimed at a deleted instruction to the next one that survives. Compare the same program without and with the optimizer:

{% call g.stage("bytecode") %} i = 0; while 1 { i += 1; if i > 3 { break; } } if 0 { print 99; } print i; {% endcall %} {% call g.stage("optimized") %} i = 0; while 1 { i += 1; if i > 3 { break; } } if 0 { print 99; } print i; {% endcall %} {{ g.h2("Tail calls") }}

When a function's last act is to call another function and return its result, as in return f(x);, the caller has nothing left to do. So instead of pushing a new frame and later returning through two of them, the callee can reuse the current frame. The peephole pass spots CALL followed by RET and turns it into TAIL_CALL:

{{ g.source("optimizer.py", "_tail_calls") }} {% call g.stage("optimized") %} func sum_to(n, acc) { if n == 0 { return acc; } return sum_to(n - 1, acc + n); } print sum_to(5000, 0); {% endcall %}

With TAIL_CALL, this recursion runs in a single frame, so sum_to(5000, 0) works. With the optimizer off it needs 5,000 frames, and the VM stops it at its limit of 1,000 nested calls. This is the one deliberate exception to the rule: an optimized program can succeed where the unoptimized one ran out of call depth.

{% call g.stage("output") %} func sum_to(n, acc) { if n == 0 { return acc; } return sum_to(n - 1, acc + n); } print sum_to(5000, 0); {% endcall %} {{ g.h2("Proving it's safe") }}

An optimizer that changes behaviour is worse than none, so MiniLang tests the rule directly. A list of tricky programs runs twice, with and without the optimizer, and the outcomes must match exactly: the same output, or the same error, with the same message and line:

{{ g.source("tests/test_optimizer.py", "SameBehaviourTests.outcome") }} {{ g.source("tests/test_optimizer.py", "SameBehaviourTests.test_snippets") }}

The programs cover the cases most likely to go wrong: division by zero inside foldable expressions, variables that may be undefined, short-circuit logic with side effects, aliased lists, and recursion. Every bug found while building the optimizer became another entry in that list.
