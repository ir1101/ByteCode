A compiler never works with your program as raw text for long. Its first stage, the lexer (also called a scanner), reads the characters once, from left to right, and groups them into tokens: the words and punctuation of the language. Every later stage works with tokens and never looks at characters again.

{{ g.h2("Characters to tokens") }}

Here is a short program, and the list of tokens the lexer hands to the parser. Spaces and line breaks have disappeared: they only ever separated tokens.

{% call g.stage("tokens") %} x = 6 * 7; print x; {% endcall %}

Each token records three things: its type, its value, and the line it started on. MiniLang has just five token types:

TypeExamplesValue
INT7, 2024the number itself (a Python int)
IDENTx, total, factthe name
KEYWORDprint, while, andthe word
OP+, <=, {, ;the symbol
EOFend of filenone

The extra EOF token at the end is a sentinel: the parser can always ask "what's the next token?" without checking whether it has run off the end of the list. A token itself is tiny:

{{ g.source("lexer.py", "Token.__init__") }}

The lexer is one loop. It looks at the current character, and that one character decides what kind of token starts here: a digit starts a number, a letter starts a word, and so on. Peeking at a character without consuming it is called lookahead, and the lexer only ever needs one or two characters of it.

{{ g.source("lexer.py", "Lexer.tokenize") }}

Two small helpers do all the moving: peek() looks ahead without moving, and advance() consumes one character.

{{ g.h2("Keywords and names") }}

When the current character is a letter, the lexer reads the whole word first, as far as letters, digits and underscores go. Only then does it decide whether the word is a keyword, by looking it up in a set:

{{ g.source("lexer.py", "Lexer.read_word") }} {{ g.source("lexer.py", start="KEYWORDS = {", end='"and", "or", "not"') }}

Why not spot keywords as they appear? Because printer starts with print, and formula starts with for. Reading the longest word first and then classifying it gets these right automatically:

{% call g.stage("tokens") %} printer = 1; format = printer + 2; print format; {% endcall %}

Numbers work the same way: read_number consumes every digit, then converts the whole run with int(). A digit followed straight away by a letter, like 12ab, is neither a number nor a name, so it's reported as an error.

{{ g.h2("Longest match") }}

Some operators are two characters long, and their first character is an operator on its own: <= starts with <, and += starts with +. The lexer always tries the two-character operators first, so it takes the longest token that fits. This rule is called maximal munch.

{{ g.source("lexer.py", start="TWO_CHAR_OPS = {", end="ONE_CHAR_OPS =") }} {% call g.stage("tokens") %} if x <= 10 { x += 1; } {% endcall %}

Without longest match, x <= 10 would become x, <, =, 10, and the parser would see an assignment where it expected a comparison. Notice that the lexer happily accepts x here even though nothing defines it: the lexer only checks spelling, not meaning. That's the job of later stages.

{{ g.h2("Comments and line numbers") }}

A # makes the lexer skip characters up to the end of the line, and spaces, tabs and line breaks are skipped as well. None of them become tokens. But line breaks aren't completely forgotten: advance() counts them, and every token is stamped with the line it started on.

{{ g.source("lexer.py", "Lexer.advance") }}

That line number travels with the token through every stage. The parser copies it into the syntax tree, the compiler copies it into each bytecode instruction, and the VM reports it when something goes wrong at runtime. A runtime error can name line 12 only because the lexer counted line breaks at the very start.

{% call g.stage("tokens") %} # a comment on line 1 total = 10; # and another print total; {% endcall %} {{ g.h2("Recovering from bad characters") }}

When a character can't start any token, such as @ or &, the lexer doesn't give up. It records an error, skips the bad run of characters, and carries on, so one run reports every bad character in the file. For characters that people bring from other languages, it adds a hint:

{{ g.source("lexer.py", "Lexer.skip_unexpected") }} {% call g.stage("tokens", expect="lex") %} x = 4 @ 2; if x > 1 && x < 9 { print x; } {% endcall %}

The errors are collected in a list, and only at the end does tokenize raise the first one, carrying all of them. Since the tokens around a bad character can't be trusted, the pipeline stops here: the parser never sees a token list with holes in it.

  • Longest match: two-character operators are tried before one-character ones.
