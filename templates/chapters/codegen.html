Everything so far has analysed the program. Code generation finally produces something to run: a flat list of numbered instructions, called bytecode, for MiniLang's stack machine (next chapter). The compiler walks the syntax tree once and emits instructions as it goes. Every instruction carries the source line it came from, so runtime errors can still name a line.

The bytecode in this chapter is shown with the optimizer off: exactly what the compiler emits, one construct at a time.

{{ g.h2("Stack code from a tree") }}

The stack machine keeps intermediate values on an operand stack. PUSH 3 puts 3 on top; ADD pops the top two values and pushes their sum. So to compile an operator node, compile its left operand, then its right, then emit the operator: by then both values are waiting on the stack. Visiting the children before the node itself is a post-order walk, and it is the whole trick:

{{ g.source("compiler.py", "Compiler.visit_BinOp") }} {% call g.stage("bytecode") %} print (1 + 2) * (7 - 4); {% endcall %}

Read the bytecode as a stack: after PUSH 1 and PUSH 2, ADD leaves 3; then PUSH 7, PUSH 4 and SUB leave 3 on top of it; MUL combines them into 9 for PRINT. The brackets have vanished: the order of instructions encodes them. This is reverse Polish notation. Each node kind has its own visit_… method, picked by the node's class name:

{{ g.source("compiler.py", "Compiler.visit") }}

Variables use LOAD name and STORE name, which move a value between a variable and the stack. A statement always leaves the stack as it found it: x = 5; pushes 5 and then STORE pops it.

{{ g.h2("Jumps and back-patching") }}

Control flow becomes jumps. JUMP addr continues at addr; JUMP_IF_FALSE addr pops a value and jumps only if it is 0. An if compiles to: the condition, a conditional jump over the then part, the then part, and (with an else) a jump over the else part.

The difficulty is that a forward jump is emitted before its target exists: when the compiler writes the jump over the then part, it doesn't yet know how long that part will be. So it emits the jump with no target, remembers its address, and fills the target in later, once it knows. This is back-patching:

{{ g.source("compiler.py", "Compiler.emit") }} {{ g.source("compiler.py", "Compiler.patch") }} {{ g.source("compiler.py", "Compiler.visit_If") }} {% call g.stage("bytecode") %} x = 3; if x > 5 { print 1; } else { print 2; } print 0; {% endcall %}

A while loop needs one forward jump (out of the loop, patched at the end) and one backward jump (to the condition, whose address is already known):

{{ g.source("compiler.py", "Compiler.visit_While") }}

break and continue are jumps too, but their targets aren't known when they're compiled either. The compiler keeps a stack of open loops; each break adds its jump to the innermost loop's list, and finish_loop patches them all once the loop is complete.

{{ g.h2("Short-circuit and/or") }}

a and b must not evaluate b when a is false. So it can't simply compile to "push a, push b, AND": there's no AND instruction at all. Instead, and and or compile into jumps that skip the right side when the left side already decides the answer. The result is always normalised to 1 or 0:

{{ g.source("compiler.py", "Compiler.visit_LogicalOp", start='if node.op == "and":', end="self.patch(to_end, self.here())") }} {% call g.stage("bytecode") %} d = 0; print d != 0 and 10 / d > 1; {% endcall %}

If d != 0 is false, JUMP_IF_FALSE leaps straight past the division to PUSH 0, so DIV never runs and there's no division by zero.

{{ g.h2("Functions") }}

The bytecode has a fixed layout: the top-level code first, then HALT, then each function body. Like semantic analysis, the compiler first collects every function, so a call can come before the definition. A call's target isn't known until the function body has been placed, so calls are back-patched at the very end:

{{ g.source("compiler.py", "Compiler.compile") }}

To call a function, the caller pushes the arguments left to right, then emits CALL addr. The function starts by STORE-ing its parameters, last one first, because the last argument is on top of the stack. return e pushes e and emits RET, and every body ends with an implicit PUSH 0; RET, which is why falling off the end returns 0:

{{ g.source("compiler.py", "Compiler.compile_function") }} {% call g.stage("bytecode") %} func area(w, h) { return w * h; } print area(6, 7); {% endcall %}

The first instruction of each function carries a label (area(w, h): above), which the disassembler prints and the VM uses to name the call in its frames.
