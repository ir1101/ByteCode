MiniLang has two kinds of value: numbers and lists. Many operations only make sense for one of them: you can't add 1 to a list, or take len of a number. The type checker works out which kind of value each name can hold, and rejects code that is certain to mix them up, before the program runs.

{{ g.h2("Static and dynamic typing") }}

A statically typed language, like Java or C, fixes each variable's type when you declare it, and the compiler rejects any program that might misuse one. A dynamically typed language, like Python or MiniLang, attaches types to values instead: a variable can hold a number now and a list later, and the check happens at runtime, when the operation actually runs:

{% call g.stage("output", stdin="1", expect="runtime") %} x = 1; print x + 1; x = [1, 2]; print len(x); input pick; if pick { x = 5; } print len(x); {% endcall %}

Lines 1 to 4 are fine, because x legally changes type. Line 7 fails, but only when it runs, and only because the input was 1: change it to 0 and the program works. MiniLang stays dynamically typed, but its type checker adds a safety net on top. It proves, before anything runs, that certain lines must fail, and reports them all at once. It has no declarations to go on, so it infers every type from the code itself.

{{ g.h2("Types as sets") }}

At each point in the program, the checker tracks the set of types a name may hold. There are only four possible sets, and they form a small lattice:

        {number, list}     could be either: no error is reported
          /         \
   {number}        {list}     known for sure
          \         /
             { }             no value reaches here
{{ g.source("typecheck.py", start='NUMBER, LIST = "number", "list"', end="NOTHING = frozenset()") }}

When two paths meet, a name's set is the union of what it could be on either path. If it's a number on one branch and a list on the other, afterwards it could be either:

{{ g.source("typecheck.py", "join") }}

Notice how this differs from definite assignment in the previous chapter, which used intersection. That analysis asked what is true on every path (a must-analysis); this one asks what is possible on some path (a may-analysis).

{{ g.h2("Inference as data flow") }}

The checker runs over the control-flow graph that the IR stage builds (chapter 5). For each block it computes the types on entry, by joining what flows in from every predecessor, then steps through the block's instructions. An assignment replaces the variable's type with the type of the new value. The blocks are revisited until nothing changes any more, which is a fixed point:

{{ g.source("typecheck.py", "Checker.flow") }}

The type of each new value follows from the instruction that makes it. Arithmetic and comparisons always produce numbers, a list literal produces a list, and reading a[i] produces whatever can be stored in lists:

{{ g.source("typecheck.py", "Checker.result") }} {% call g.stage("types") %} n = 5; xs = [1, 2, 3]; size = len(xs); maybe = 1; if n > 3 { maybe = xs; } {% endcall %}

maybe is a number on one path and a list on the other, so the checker reports it as either.

{{ g.h2("Across functions") }}

A function's parameters have no types written down, so the checker gathers them from every call site: a parameter's type is the union of the argument types it's ever called with. A call's type is the union of everything the function can return. Since functions call each other, and even themselves, these facts feed one another, so the whole program is analysed again and again until nothing changes:

{{ g.source("typecheck.py", "Checker.contribute") }} {{ g.source("typecheck.py", "Checker.run") }} {% call g.stage("types") %} func first(xs) { return xs[0]; } func wrap(v) { return [v]; } func fact(n) { if n <= 1 { return 1; } return n * fact(n - 1); } print first(wrap(fact(4))); {% endcall %}

fact is recursive, so its return type depends on itself. The fixed point settles it: the first round sees only return 1 (a number); the next round sees that n * fact(n - 1) is a number too, and nothing changes after that.

{{ g.h2("Only certain errors") }}

Once the fixed point is reached, the checker looks at every operation once more. It reports an error only when an operand's set is exactly the wrong type: {list} where a number is needed, or {number} where a list is needed. If a value could be either, the line might work, so it is left for the VM to check at runtime. That way a program that could run correctly is never rejected:

{{ g.source("typecheck.py", "Checker.check", start='if op == "binop"', end="is a list\", line)") }} {% call g.stage("types", expect="type") %} xs = [1, 2]; n = 7; print xs * 2; print n[0]; if xs { print 1; } print len(n); {% endcall %}

All four mistakes are reported in one run, and each message names the culprit. Compare this program, where the checker can't be sure:

{% call g.stage("types") %} x = 1; input flag; if flag { x = [1]; } print x + 1; {% endcall %}

No type error: x + 1 works whenever flag is 0. If it isn't, the VM still stops it at runtime.
