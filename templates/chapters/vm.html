The last stage runs the bytecode. MiniLang's virtual machine (VM) is a stack machine: a simulated computer, written in Python, whose instructions take their inputs from an operand stack and leave their results on it. Real processors work with registers instead, but stack machines are simple and compact, which is why the Java VM and Python's own interpreter work this way too.

{{ g.h2("Fetch, decode, execute") }}

The whole machine is one loop around a program counter (pc), the address of the next instruction. Each turn fetches the instruction at pc, moves pc on, decodes its opcode, and executes it. Jumps work simply by setting pc to somewhere else:

{{ g.source("vm.py", "VM.run", start="def run(self):", end='elif op == "POP":') }}

The trace below records the machine after every instruction: its address, the instruction, and the stack once it has run. It's shown with the optimizer off, so you see every instruction the compiler emitted:

{% call g.stage("trace") %} x = 4; print x * 2 + 1; {% endcall %}

The loop stops when pc runs off the end, which HALT arranges by setting it there.

{{ g.h2("The operand stack") }}

Every intermediate value lives on the operand stack. A binary operator pops its right operand first, because it was pushed last, and then its left one. For ADD that order doesn't matter, but for SUB, DIV and the comparisons it does:

{{ g.source("vm.py", "VM.run", start="elif op in BINARY_OPS:", end="self.stack.append(apply_binary(op, a, b, ins.line))") }}

The arithmetic itself lives in apply_binary. The optimizer calls the very same function when it folds constants, so compile-time and runtime results can never disagree. Its division rounds toward zero, like C and Java, rather than down like Python's //:

{{ g.source("vm.py", "apply_binary", start='if op == "DIV":', end="return a - b * _trunc_div(a, b)") }} {% call g.stage("trace") %} print 20 - 6; print -7 / 2; {% endcall %}

Watch the stack after PUSH 6: it holds [20, 6], with 6 on top. SUB pops b = 6, then a = 20, and pushes a - b. Each statement leaves the stack empty again.

{{ g.h2("Frames and the call stack") }}

Next to the operand stack, the VM keeps a call stack of Frames, one per active function call. A frame holds that call's local variables, and the address to return to:

{{ g.source("vm.py", "Frame") }}

CALL pushes a new frame, remembering where to come back to, and jumps into the function. RET pops the return value, drops the frame, jumps back, and pushes the value for the caller. LOAD looks in the current frame's locals first, then in the globals. That's MiniLang's scope rule, enforced at runtime:

{{ g.source("vm.py", "VM.run", start='elif op == "CALL":', end="self.stack.append(value)") }}

Because recursion runs on this call stack, not on Python's, every call to a recursive function gets its own frame with its own copy of n:

{% call g.stage("trace") %} func fact(n) { if n <= 1 { return 1; } return n * fact(n - 1); } print fact(3); {% endcall %}

The trace shows the depth growing to 3 as the calls stack up, then unwinding as each RET hands a value back. While fact(1) runs, the two calls underneath are waiting with 3 and 2 on the operand stack. TAIL_CALL (chapter 6) is the one exception: it reuses the current frame instead of adding one.

{{ g.h2("Runtime errors and limits") }}

Some mistakes can only show up while the program runs: dividing by a value that happens to be 0, an index past the end of a list, input that has run out. The VM checks before every risky operation and raises a VMError carrying the instruction's source line, so the message still points at your code:

{{ g.source("vm.py", "VM.check_index") }}

It also refuses to run forever. Code arriving from a browser shouldn't be able to hang the server, so the VM has three limits: a number of steps (one million in the playground), a number of printed lines, and a call depth of 1,000:

{% call g.stage("output", expect="runtime") %} func down(n) { return 1 + down(n + 1); } print down(0); {% endcall %}

Everything printed before an error is kept, and in the playground the step-through opens at the last good step, so you can see the state that led to the error.

{{ g.h2("Tracing") }}

The VM itself knows nothing about traces or the playground's step-through. It just calls an optional on_step hook after each instruction, handing over itself. The command line's --trace option plugs in a hook that prints one line per step; that's the text in every Try it box on this page:

{{ g.source("vm.py", "text_tracer") }}

The playground plugs in a different hook, which copies the stack, the globals and every frame's locals into a list after each step. That list is the JSON the step-through view scrolls through, which is why you can step backwards as well as forwards:

{{ g.source("api.py", "_trace_recorder", start="def record(addr, ins, vm):", end='"lines_printed": vm.lines_printed,') }}

Values are copied with _snapshot as they are recorded. Lists are shared by reference, so without a copy, a later a[0] = 9 would rewrite every earlier step of the history.
