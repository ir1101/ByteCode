A syntax tree is great for checking a program, but awkward for reasoning about how values flow through it. So the compiler also lowers the tree to an intermediate representation (IR): a list of very simple instructions, cut into basic blocks and joined into a control-flow graph. Over that graph it runs data-flow analyses, which answer questions like "is x always 10 here?" and "will anyone ever read this value?".

{{ g.h2("Three-address code") }}

MiniLang's IR is three-address code (TAC): every instruction does at most one operation, on at most two operands, and stores the result. An expression like 2 * (3 + y) becomes a sequence of steps, with the intermediate results in compiler-made temporaries t1, t2, …:

{% call g.stage("ir") %} y = 4; x = 2 * (3 + y); print x; {% endcall %}

Each instruction is a Quad: an operation, a destination, its operands, and a jump target for jumps. Lowering an expression is a short recursive function: lower the operands first, then emit one instruction that combines them into a new temporary:

{{ g.source("ir.py", "Lowerer.expr", start="if isinstance(node, BinOp):", end="return out") }}

Control flow becomes labels and two kinds of jump: goto L, and if_false t goto L. Here is how a while loop is lowered:

{{ g.source("ir.py", "Lowerer.stmt", start="elif isinstance(node, While):", end='self.emit("label", target=end)') }}

Temporaries print as t1 but are stored under the key %t1 internally. % can't appear in a MiniLang name, so a variable the programmer happens to call t1 can never be confused with a temporary.

{{ g.h2("Basic blocks") }}

A basic block is a run of instructions that always execute together: control enters only at the top and leaves only at the bottom. Within a block there are no branches, which makes it the natural unit for analysis. Blocks are found by marking the leaders, the instructions that start one:

  • the very first instruction,
  • every label (something may jump there),
  • every instruction straight after a jump or a return.
{{ g.source("ir.py", "build_cfg", start="for quad in proc.quads:", end="current.quads.append(quad)") }} {% call g.stage("ir") %} input n; if n % 2 == 0 { print 0; } else { print 1; } print n; {% endcall %}

The if becomes four blocks: B0 reads n and tests the condition, B1 and B2 are the two branches, and B3 is where they join. (n comes from input so that nothing here is a known constant; with n = 7, constant propagation would prove the first branch can never run.)

{{ g.h2("The control-flow graph") }}

Joining every block to the blocks that can run straight after it gives the control-flow graph (CFG). A block ending in goto has one successor. A block ending in if_false has two: the next block, and the jump target. A block ending in return has none. Anything else falls through to the next block.

A loop shows up as a back edge: an edge to a block that comes earlier. In the playground's IR tab these are the dashed arrows on the left.

{% call g.stage("ir") %} i = 0; total = 0; while i < 4 { total += i; i += 1; } print total; {% endcall %}

B2, the loop body, ends with goto L1 back to B1, the condition. That edge is why analyses over a CFG have to iterate: what B1 knows depends on B2, which depends on B1.

{{ g.h2("Constant propagation") }}

The first analysis asks: which variables hold a known constant at the start of each block? It's a forward analysis using Kildall's algorithm. Start from "nothing known" at the entry; push facts through each block's instructions; where paths join, keep a fact only if every incoming path agrees on the same value:

{{ g.source("ir.py", "meet") }} {{ g.source("ir.py", "propagate") }}

The loop runs until nothing changes. That always happens, because facts can only ever be removed, never added. It also skips branches it can prove are never taken (live_successors), so a dead branch doesn't spoil the facts at the join. Below, the optimized view shows the TAC with every proven constant substituted and folded:

{% call g.stage("constants") %} x = 10; y = x * 2; if y > 5 { z = y + 1; } else { z = 0; } print z; {% endcall %}

Constants flow all the way through: y is 20, so y > 5 is true, the else branch can never run, and z is 21 at the join. Notice that some assignments are now marked as dead stores. That's the next analysis.

{{ g.h2("Liveness") }}

A variable is live at a point if its current value may still be read later, on some path. Liveness flows backwards: whether x is live depends on what comes after. For each block:

live_out(B) = union of live_in(S) over every successor S
live_in(B)  = use(B) ∪ (live_out(B) − def(B))

Inside a block, the analysis walks backwards from live_out: each instruction first kills the variable it writes, then adds the variables it reads. So i = i + 1 still keeps i live before it:

{{ g.source("ir.py", "live_after_each") }} {{ g.source("ir.py", "liveness") }}

A store to a variable that isn't live right after it is a dead store: its value is overwritten, or the program ends, before anyone reads it. The IR view lists each block's live variables and tags dead stores:

{% call g.stage("ir") %} result = 0; result = 6 * 7; count = 3; while count > 0 { count -= 1; } print result; {% endcall %}

The first result = 0 is dead: line 2 overwrites it before anything reads it. That's what semantic analysis turns into a warning, and what the optimizer deletes. These analyses complete a classic set:

  • Three-address code: one operation per instruction, with temporaries for intermediate results.
  • A basic block runs start to finish; leaders are the first instruction, labels, and whatever follows a jump.
  • The CFG joins blocks by their possible successors; loops are back edges.
  • Data-flow analyses iterate over the CFG to a fixed point, forward or backward.
  • Constant propagation finds known values; liveness finds dead stores.
